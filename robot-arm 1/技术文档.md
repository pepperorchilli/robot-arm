# 三、关键技术决策

## 决策 1：为什么用 PCA9685 而不是 ESP32 直驱

ESP32 的硬件 PWM 通道有限，且直接驱动会让 5 根信号线从 ESP32 一路拉到机械臂——
线长、贴近天线。PCA9685 把 PWM 的产生挪到了靠近舵机的位置，
ESP32 只需 2 根 I2C 线。

> 这个决策在后来排查抖动时被验证是对的（见第四节"绕开 PCA9685 反而更糟"）。

## 决策 2：为什么让 ESP32 主动连出

**问题**：ESP32 在局域网里，没有公网 IP，外面访问不进来。

| 方案 | 问题 |
|---|---|
| 端口映射 | 需要路由器管理权限，且暴露家庭内网 |
| 内网穿透（frp/ngrok） | 要额外跑服务，免费版不稳定 |
| **设备主动连出** | ESP32 主动连服务器并保持长连接，服务器顺着这条连接往回发命令 |

选了第三种——这是**物联网设备的标准做法**。

## 决策 3：为什么加 token 鉴权

服务器地址是公开的。如果不校验，任何人只要知道地址，就能伪造设备连接、劫持控制权。

```js
const token = url.searchParams.get('token');
if (token !== config.ESP32_TOKEN) ws.close();
```

# 四、★ 排查过程记录

**这是这一代最有价值的部分。**

## 4.1 问题的发现（08-15）

系统跑通后，发现一个现象：

> **5 个舵机静止锁定时，全部有小幅抽搐，不同步。**
> **不承重（空载）也会抖。**

于是开始了排查。当时创建了 `servo-direct/servo-direct.ino`（单舵机直驱测试）
作为诊断工具。

## 4.2 排查思路

舵机抖动可能的原因有几类：

```
          ┌── 舵机自身：电位器磨损、死区过大
抖动原因 ─┼── 驱动电路：PCA9685 输出不稳
          ├── 供电：电压跌落、纹波过大
          ├── 机械：齿轮虚位、负载
          └── 信号：外部干扰耦合进信号线
```

思路是**逐个排除**：每次只改变一个变量，看抖动是否消失。

## 4.3 逐步排除

| 怀疑对象 | 验证方法 | 结果 | 结论 |
|---|---|---|---|
| PCA9685 板故障 | 拆掉 PCA，改 ESP32 直驱 | **仍然抖** | ❌ 排除 |
| 个别舵机损坏 | 观察是否只有特定舵机抖 | **全部都会抖** | ❌ 排除"个别坏件" |
| 供电不足 | 查电源余量；观察空载是否还抖 | 5V 20A 余量充足，**空载也抖** | ❌ 排除欠压振荡 |
| 机械虚位 | 空载测试 | **空载也抖** | ❌ 排除机械问题 |
| **外部干扰** | 隔离干扰源 | **不抖了** | ✅ **确诊** |

## 4.4 一个反直觉的发现

排查中把 PCA9685 拆掉、改成 ESP32 直接驱动舵机——**结果抖动反而更严重了**。

这个"失败"的尝试其实很有价值，它反向验证了干扰的来源：

| | PCA9685 方案 | 直驱方案 |
|---|---|---|
| PWM 从哪来 | PCA 芯片自己产生 | ESP32 的 GPIO |
| 信号线起点 | 从 PCA 出发（**离射频源远**） | **从 ESP32 出发（就是射频源本身）** |
| 信号线长度 | 短 | 长（要从 ESP32 拉到机械臂） |
| 5 根线的关系 | 从 PCA 出来 | 从**相邻 GPIO** 出来，天然并排 |

**直驱把"信号源"搬到了干扰源旁边，还顺手把天线加长了。**

## 4.5 决定性实验（09-02）

前面的排除都指向"外部干扰"，但需要确证。做了这个实验：

> **烧录 `wifi-off-hold-test.ino`：不开 WiFi，纯硬件锁死 5 个舵机。**

```
结果：完全不抖。
```

**确诊**：ESP32 的 **2.4GHz WiFi 射频**（含地弹）耦合进了未屏蔽的信号线。

### 为什么会导致抽搐

模拟舵机靠**量脉宽长度**决定角度（0.5–2.5ms 对应 0–180°）。

静止时固件不再写 PWM，信号本是一条恒定脉宽。但 WiFi 发包瞬间的射频毛刺
耦合进信号线，让脉宽被撑长或削短几微秒——**舵机就把它当成一次角度变化**。

不同舵机、不同时刻的耦合强度不同 → 看起来"异步、小幅"。

## 4.6 当时的整改尝试

在这一代里做了电源侧的整改：

- 在 2进12出分电盒输入端并联 **1000µF 电解电容**
- 舵机信号/电源走线分离

**结论：没有解决问题。**

原因很明确——**电源电容滤的是电源纹波和瞬态压降，而干扰走的是
"空气 → 信号线"这条路径，根本不经过电源线。**

这是一个重要的认知：**滤错了对象，再大的电容也没用。**

正确的做法应该是在**信号线两端**处理：
- PCA9685 输出端串 100Ω（磨圆陡边沿）
- 舵机信号输入端对地并 1–4.7nF（旁路射频）

# 五、这一代的局限

排查到最后，得出的核心结论是：

> **这是模拟舵机的架构性矛盾，不是接线问题。**

模拟舵机只能靠脉宽传递角度，任何叠加在信号线上的噪声都会被"翻译"成角度。
加电容电阻是在**信号完整性层面打消耗战**，成功率有限。

| 遗留问题 | 说明 |
|---|---|
| **抖动** | 根因已定位，但未根治 |
| 数据存储 | JSON 文件，全量读写、有竞态 |
| 前端 | 原生 JS 单文件，难维护 |
| 接口文档 | 无 |
| 力反馈 | 模拟舵机不支持 |

**这些正是第二代要解决的。**

# 九、这段经历的价值

排查本身比"跑通系统"更有含金量：

1. **完整的科学方法**：假设 → 设计实验 → 逐个排除 → 定位根因
2. **接受"失败"的尝试**：直驱方案失败了，但它反向验证了干扰来源
3. **识别出架构性问题**：没有停留在"多加几个电容试试"，而是判断出
   这是模拟舵机的原理性缺陷
4. **知道什么时候该换方案**：在信号完整性层面继续投入是边际递减的，
   换架构才是正解

> 面试时这段比"我会用什么框架"更有说服力——它体现的是**工程判断力**。
