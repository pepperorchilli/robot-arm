# 五自由度机械臂（含夹爪） · 系统技术文档

一份从硬件到云端的完整技术说明，解释这个系统**由什么组成**、**怎么运作**、以及**每个技术选择背后的原因**。

---

# 一、系统总览

## 它是什么

一台 3D 打印的五自由度机械臂（底座、肩、肘、腕俯仰、腕旋转，再加一个夹爪，共 6 个舵机），可以通过网页远程控制，也能用手势识别驱动。

机械结构采用 **SO-ARM101** 开源设计（Hugging Face LeRobot 项目的官方硬件）。

**六个自由度**（从下到上，与舵机编号一致）：

| 编号 | 关节 | 作用 |
|---|---|---|
| 0 | 底座旋转 | 水平旋转 |
| 1 | 肩部 | 抬升/下降 |
| 2 | 肘部 | 俯仰 |
| 3 | 腕俯仰 | 调整末端角度 |
| 4 | 腕旋转 | 末端自转 |
| 5 | 夹爪 | 抓取/松开 |

## 四层架构

```
┌─────────────────────────────────────────────────────┐
│  应用层    Vue 3 网页遥控  │  Python 手势识别            │
└──────────────────────┬──────────────────────────────┘
                       │ HTTP
┌──────────────────────▼──────────────────────────────┐
│  云服务层   Node.js + Express + WebSocket 中转         │
│            MySQL 数据持久化  │  OpenAPI 接口文档         │
└──────────────────────┬──────────────────────────────┘
                       │ WebSocket 长连接
┌──────────────────────▼──────────────────────────────┐
│  嵌入式层   ESP32-S3 固件（C++ / Arduino）             │
│            自实现的 STS / SCS 协议栈（无第三方库）      │
└──────────────────────┬──────────────────────────────┘
                       │ TTL 半双工串口 · 1Mbps
┌──────────────────────▼──────────────────────────────┐
│  硬件层     总线舵机转接板 (H2)  │  STS3215 × 6       │
│            3S 锂电 12.6V 直通  │  SO-ARM101 打印件    │
└─────────────────────────────────────────────────────┘
```

> **这一代没有的东西**：一代的 **PCA9685 驱动板、UBEC 降压、分电盒全部去掉了**。
> 总线舵机是一根数据线串到底（菊花链），角度以数字报文传递，
> 不需要中间再有一块板子去"产生 PWM"。详见第三节。

# 二、一次完整的数据流

**以"在网页上把底座转到 45°"为例，追踪整条链路。**

### ① 用户拖动滑块

浏览器里的 Vue 组件 `ServoCard.vue` 收到 `input` 事件，通过 `defineModel()` 把新值同步给父组件。

### ② 前端节流

`useArmControl.js` 里的 `setAngle()` 做 **60ms 节流**——拖动时每秒触发几十次事件，每次都发请求会把 ESP32 打爆。节流后只发最后一次。

```js
fetch('/set?servo=0&angle=45')
```

### ③ HTTP 请求到达服务器

Express 路由 `app.get('/set')` 命中：

```js
const cmd = servo + ':' + angle;   // "0:45"
if (esp32) esp32.send(cmd);        // 通过 WebSocket 发出
else res.status(503)               // 设备不在线
```

**注意 503**：网页和手势模块都用这个状态码判断"机械臂是否在线"。

### ④ WebSocket 转发到 ESP32

ESP32 在局域网/内网，没有公网 IP。它在启动时就**主动连出来**，和服务器建立一条长连接并保持。服务器拿到浏览器命令后，顺着这条已有连接往回发。

### ⑤ 固件解析命令

```cpp
void onMessage(WStype_t type, uint8_t* payload, size_t length) {
  String msg = String((char*)payload);          // "0:45"
  int idx = constrain(msg.substring(0, colon).toInt(), 0, NUM - 1);
  int tgt = constrain(msg.substring(colon + 1).toInt(), 0, 180);
  target[idx] = tgt;
  applyTargets();      // 立刻下发，不等主循环
}
```

### ⑥ 一条 SYNC_WRITE 广播给全部 6 个舵机

`applyTargets()` 把所有目标角度换算成舵机量程，然后用**一条指令**广播：

```cpp
void applyTargets() {
  uint16_t pos[NUM];
  for (int i = 0; i < NUM; i++) pos[i] = angleToPos(target[i]);
  syncWritePosition(pos, NUM);      // 发给广播 ID 0xFE
}
```

报文格式（Feetech SCS / Dynamixel 1.0 兼容）：

```
FF FF FE LEN 83 2A 02 │ ID1 位置低 位置高 │ ID2 位置低 位置高 │ … │ 校验和
                       └── 一个舵机 3 字节，一条包带完 6 个 ──┘
```

**一代的 `stepMotion()` 逐度插补到这里就没有了。**
一代必须在主循环里每 15ms 给每个舵机 ±1 度，是因为模拟舵机只认"当前脉宽"，
没有"目标 + 时间"这个概念；总线舵机收下目标位置和 `MOVE_TIME = 400ms` 之后，
**自己按时间规划速度走过去**。

> 这是"选对架构，代码反而更简单"的具体例子：一代最难写的那段运动控制，
> 二代直接删掉了——它本来就是在替舵机做舵机自己就能做的事。

### ⑦ 舵机转动

舵机自己按 `MOVE_TIME` 做速度规划转到位，**整个过程 ESP32 不参与**。

注意**目标角度和舵机量程不是同一个尺子**：网页上还是 0~180°，
固件用 `map(a, 0, 180, 0, 2048)` 映射到舵机 0~2048（即 0~180° 机械角），
**另外一半量程刻意留着**，给以后需要更大行程的关节。

### ⑧ 主循环空出来做轮询

不用插补之后，主循环腾出来读只读寄存器：

```cpp
void loop() {
  ws.loop();       // 保持通信，必须高频调用
  pollJoint();     // 一次 loop 只读一个关节，6 个轮着来
}
```

**为什么一次只读一个**：读寄存器是**同步等回包**的——半双工总线上发完请求要等舵机应答。
一口气读完 6 个会让 `loop()` 卡住几百毫秒，期间 `ws.loop()` 得不到调用，
**心跳就断了**，表现是"控制到一半掉线"。轮询把它摊平到 6 次循环里。

### ⑨ 到位回报与遥测

这是**两条不同的上报**，别混：

**到位回报**——`applyTargets()` 会预约一个时刻（`MOVE_TIME + 50ms`，即舵机该走到位之后）：

```
0:45,1:90,2:90,3:90,4:90,5:150
```

**遥测**——主循环轮询到的原始寄存器值，一个关节一条：

```
T:0,2048,15,124,32,0
   │  │    │  │   │  └ 电流
   │  │    │  │   └─── 温度
   │  │    │  └─────── 电压
   │  │    └────────── 负载  ← 力反馈/碰撞感知就靠它
   │  └─────────────── 位置
   └────────────────── 关节编号
```

**固件只丢原始寄存器值上来，不做单位换算**——电压 ×0.1V、电流 ×6.5mA 这些
全放在服务器做。这样以后改显示、加图表，不用重新烧录一块拆装很麻烦的板子。

# 三、硬件层

> 这一章讲的是**第二代当前的硬件**。
> 一代的 `PCA9685 + 模拟舵机（MG996R）` 方案与当时的接线，见
> [`../robot-arm 1/技术文档.md`](../robot-arm%201/技术文档.md)——
> 它是被取代的方案，但排查过程仍然有效，第六节会用到。

## 舵机：STS3215（总线舵机）

| 参数 | 值 |
|---|---|
| 型号 | Feetech **STS3215**（SO-ARM101 官方 BOM） |
| 工作电压 | **C047 版 4 – 14 V**（本项目 3S 锂电 12.6V 直通） |
| 控制方式 | TTL 半双工串口，**1 Mbps** |
| 分辨率 | 0 – 4095 对应 0 – 360° |
| 反馈 | 位置 / 负载 / 电压 / 温度 / 电流，**全部可读** |

**工作原理**：舵机内部是闭环的。控制板收下"目标位置 + 时间"之后自己规划速度走过去，
并且随时可以回读当前位置和**负载**——力反馈、碰撞感知、过温低压保护都建立在这一点上。

> ⚠️ **买之前必须确认型号版本**：STS3215 有 **C001（7.4V）** 和 **C047（4–14V）** 两种，
> 外观几乎一样。官方 BOM 里 **Leader 臂用 7.4V 版**（手拖示教、不出力），
> **Follower 臂必须用 C047**。本项目不做 Leader（网页控制台取代了它），6 个全要 C047。
> **C001 接到 12.6V 总线上会瞬间烧掉。**

## 总线：一根线串到底

```
ESP32 GPIO16 (TX) ──> 转接板 H2 的 TX
ESP32 GPIO17 (RX) ──> 转接板 H2 的 RX
ESP32 GND         ──> 转接板 GND
```

6 个舵机是**菊花链**（一个串一个），共用这一根数据线。

**为什么一根线能带 6 个**：每个舵机有唯一 **ID**，指令里带 ID，只有对应的舵机应答。
出厂 ID **全是 1**，必须逐个改成 1~6，否则会互相抢答。

> ⚠️ **别接开发板丝印上的 `TX` / `RX`**。ESP32-S3 开发板上印着那两个字的脚是
> **GPIO43/44（UART0 调试口）**，不是固件使用的 GPIO16/17。
> 接错的症状是**总线一个字节都收不到**——排查时在这个坑里耗掉过一整天，
> 详见 [`演进记录.md`](演进记录.md) 坑 1。

## 供电：3S 锂电直通

```
3S 锂电 12.6V ─────────────┬──> 舵机总线（V+ / GND，6 个舵机并联）
                           └──> 不再降压

Mac ──USB──> ESP32-S3      ← 供电 + 串口日志，一根线两用
```

舵机工作范围 4–14V，**满电 12.6V 可以直通，不需要 UBEC 降压**——
一代那条 `12.6V → UBEC 5V → 分电盒` 的链子整条省掉了。

**三条必须遵守的**：

1. **必须共地**——ESP32 的 GND 要接到电池负极。半双工 TTL 靠一根线收发，
   没有共同参考电平就不稳。（ESP32 用 USB 供电时地来自电脑，
   电脑地和电池负极短接是安全的，电池浮地。）
2. **绝对不要把 12.6V 灌进 ESP32**——会瞬间烧毁。
3. **上电顺序：先 USB，后电池**。舵机先上电时数据线被舵机驱动着，会和 ESP32 抢总线。

> 用墙上电源代替电池：需要 **12V 5A 以上**（10A 更稳）。
> ⚠️ 官方 BOM 默认给的是 **5V** 电源，那是配 7.4V 舵机用的，**别照抄**。

# 四、嵌入式层

## ESP32-S3

- 双核 Xtensa LX7，240MHz
- 内置 **2.4GHz WiFi**（本项目用它的 STA 模式连路由器）
- 用到的外设：**UART1**（半双工，接舵机总线）、UART0（串口日志）、WiFi
- 型号 ESP32-S3-WROOM-1 **N16R8**（16MB Flash / 8MB PSRAM）

## 固件的两种模式

| 模式 | 代表固件 | 特点 |
|---|---|---|
| **softAP 自建热点** | `arm-bus-servo/` | ESP32 自己开热点，电脑直连它的 IP。简单，但**只能局域网**；带串口调试命令，适合单测总线协议 |
| **STA 连路由器 + WebSocket** | `arm-cloud-bus/` | **当前主线**。ESP32 主动连服务器，可**公网访问** |

> 一代对应的两个固件（`servo-test.ino` / `arm-cloud.ino`）已归档到
> [`../robot-arm 1/`](../robot-arm%201/)。选型表见 [`../固件演进记录.md`](../固件演进记录.md)。

## 主循环为什么不阻塞

**反面教材**（一代早期的写法）：

```cpp
while (angles[idx] != tgt) {      // ❌ 阻塞
  angles[idx] += step;
  writeServo(idx, angles[idx]);
  delay(15);
}
```

问题有二：
1. `delay` 期间 `loop()` 卡死，**WebSocket 收不到新消息、心跳发不出去**，服务器会判定设备掉线
2. 多轴只能一个一个动

**二代的写法更简单——因为这项工作整个消失了**：

```cpp
void loop() {
  ws.loop();       // 通信优先
  pollJoint();     // 一次读一个关节的遥测（见 ⑧）
}
```

舵机自己会按 `MOVE_TIME` 平滑走位，固件不需要再"推进"任何东西。
一代那段最难写、最容易出 bug 的运动控制代码，二代直接不存在了。

> 但 `loop()` 依然有阻塞风险，只是换了个地方：**读寄存器要同步等回包**。
> 所以遥测是**一次循环读一个关节**，而不是一口气读完 6 个——详见 ⑧。

## 通信健壮性

```cpp
ws.setReconnectInterval(5000);        // 断了自动重连
ws.enableHeartbeat(15000, 3000, 2);   // 心跳保活
```

**心跳为什么必要**：家用路由器和运营商的 NAT 会掐断长时间空闲的 TCP 连接。没有心跳的话，连接看着还在，实际已经死了，命令发不进去。

## 上电自检

开机先 **PING 一遍 6 个 ID**，谁不在线当场报出来：

```
总线自检: 1✓ 2✓ 3✓ 4✓ 5✗ 6✓ (5/6)
```

这一步价值很高：**它把"接线/供电问题"和"协议问题"当场分开了**。
自检全 ✗ 就去查线，自检通过但动作不对才去查协议——省掉大量瞎猜。

# 五、云服务层

## 为什么需要服务器中转

**核心矛盾**：ESP32 在局域网里，**没有公网 IP**。

三种解法对比：

| 方案 | 问题 |
|---|---|
| 端口映射 | 需要路由器管理权限，且暴露家庭内网 |
| 内网穿透（frp/ngrok） | 要额外跑一个服务，免费版不稳定 |
| **设备主动连出（本项目）** | ESP32 主动连服务器并保持长连接，服务器顺着这条连接往回发命令 |

第三种是**物联网设备的标准做法**——不需要公网 IP，不用改路由器。

## 技术栈

**Express**：提供 REST API 和静态站点托管

**ws 库**：WebSocket 服务端，与 Express 共用同一个 HTTP server

**设备鉴权**：ESP32 连接时必须在地址里带 token

```js
const token = url.searchParams.get('token');
if (token !== config.ESP32_TOKEN) {
  ws.close();   // 不对就断开
}
```

**为什么需要**：否则任何人只要知道服务器地址，就能伪造设备连接、劫持控制权。

## MySQL 数据持久化

留言板从 JSON 文件迁移到 MySQL：

| | JSON 文件 | MySQL |
|---|---|---|
| 并发 | 全量读写，有竞态 | 行级锁，并发安全 |
| 查询 | 全部读进内存 | 索引加速 |
| 关联 | 手工维护 | 外键约束 |

**两个具体优化**（详见 `server/DATABASE.md`）：

- **索引优化**：给 `created_at` 加索引后，列表查询扫描行数从 **49914 → 20**，耗时 **11.76ms → 0.30ms**
- **消除 N+1 查询**：列表接口从"1 条留言查 1 次回复"（1+N 次查询）改为用 `IN` 批量取回再内存归组（**固定 2 次**）

## 接口文档

**OpenAPI 3.0 + Swagger UI**，注解以 JSDoc 形式写在路由上方，文档与代码同步维护。

访问 `/api-docs` 可在线调试，`/api-docs.json` 可导入 Postman。

# 六、关键技术问题：抖动

这是本项目**最有价值的一段工程经历**。

## 现象

5 个舵机静止锁定时，全部有小幅抽搐，**不同步**。空载也抖。

## 排查过程（逐步排除）

| 怀疑对象 | 验证方法 | 结论 |
|---|---|---|
| PCA9685 板坏了 | 拆掉改直驱，仍抖 | ❌ 排除 |
| 个别舵机坏 | 全部都会抖 | ❌ 排除 |
| 供电不足 | 5V 20A 余量充足，空载也抖 | ❌ 排除 |
| 机械虚位 | 空载也抖 | ❌ 排除 |
| **WiFi 射频** | **关掉 WiFi 烧录 → 完全不抖** | ✅ **确诊** |

## 根因

**ESP32 的 2.4GHz WiFi 射频耦合进了那 5 根未屏蔽的信号线。**

模拟舵机靠"量脉宽长度"决定角度。射频毛刺叠上去，脉宽被撑长或削短几微秒，舵机就把它当成一次角度变化 → 抽搐。不同舵机耦合强度不同 → 看起来"异步"。

## 为什么直驱反而更糟

| | PCA9685 方案 | 直驱方案 |
|---|---|---|
| PWM 从哪来 | PCA 芯片自己产生 | ESP32 GPIO |
| 信号线起点 | 从 PCA 出发（**远离射频源**） | **从 ESP32 出发（就是射频源）** |
| 信号线长度 | 短 | 长 |

直驱把"信号源"搬到了射频源旁边，还顺手加长了天线。

## 两种解决思路

**思路 A：信号完整性层面压制**（治标）

- 每根信号线串 100Ω 电阻，磨圆陡边沿
- 每个舵机信号端对地并 1–4.7nF 电容，旁路射频
- 星形接地，信号线远离天线

成功率约 70–85%，需要反复调试。

**思路 B：换架构**（治本）

改用**串行总线舵机**（如 Feetech STS3215）：

```
传统舵机：  ──PWM 脉宽（模拟量）──>  舵机
总线舵机：  ──数字协议帧 + 校验和──>  舵机
```

总线舵机的指令是有帧格式的：

```
0xFF 0xFF ID LENGTH INSTRUCTION 参数... 校验和
```

噪声混进来，要么被数字电平阈值滤掉，要么**造成校验失败被舵机直接丢弃**——永远不会翻译成角度。

**这是协议层面的免疫，不是靠滤波压制。**

**附加收益**：总线舵机是闭环的，能回传当前位置和**电流**。电流 ≈ 力矩，于是可以做**力反馈**——夹爪抓握力度控制、碰撞检测、堵转保护。这是模拟舵机做不到的（它只有一根信号线进，什么都不回）。

# 七、应用层

## Vue 3 网页遥控

**技术栈**：Vue 3.5 + Vite 8 + 单文件组件

**目录结构**：

```
web/src/
├── App.vue                      主页面
├── components/ServoCard.vue     舵机卡片（可复用组件）
└── composables/useArmControl.js 控制逻辑
```

**设计要点**：

- **逻辑与视图分离** —— 控制逻辑全在 composable 里，组件只管渲染。将来换成 WebSocket 或接入手势输入，组件一行都不用改
- **`defineModel()` 双向绑定** —— 子组件不需要知道父组件怎么存数据
- **节流** —— 拖动只发最后一次，按钮点击不节流（保证即时响应）

## Python 手势识别

**技术栈**：MediaPipe + OpenCV

**流程**：摄像头 → 手部 21 个关键点 → 手指伸展判定 → 手势分类 → HTTP 命令

**核心算法**：判断手指是否伸直，常见做法是"指尖 y 坐标比指节小"，但**这要求手掌必须竖直朝上**，手一歪就判错。

本项目改用**距离比较**：

```
伸直 → 指尖伸得更远 → 指尖到掌心的距离 > 指节到掌心的距离
弯曲 → 指尖收回掌心 → 距离反而更小
```

这个方法与**手掌朝向、旋转、离镜头远近都无关**，稳得多。

**两种模式**：
- 指令模式：固定手势触发固定动作（张开/握拳/数字…）
- 跟随模式：手掌位置实时映射到底座和大臂角度
