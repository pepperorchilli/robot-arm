# 一、为什么要做第二代

第一代（`robot-arm 1/`）把云链路跑通了——ESP32 主动连出、公网可遥控、网页能操作。
但留了一个**没根治**的问题：

> 5 个舵机静止锁定时小幅抽搐，**不同步**，而且**空载也抖**。

一轮完整的排查（逐个排除 PCA9685 / 舵机个体 / 供电 / 机械虚位），
最后用决定性实验定案：**烧一个不开 WiFi、纯硬件锁死舵机的固件 → 完全不抖**。

根因是 **ESP32 的 2.4GHz 射频耦合进了未屏蔽的 PWM 信号线**。

关键在于——**这是模拟舵机的架构性矛盾，不是接线问题**：

| | 模拟舵机 | 串行总线舵机 |
|---|---|---|
| 角度怎么传 | 脉宽长度（0.5–2.5ms），**模拟量** | 数字报文，**带校验和** |
| 信号线上的噪声 | 被直接翻译成角度 → 抽搐 | 被电平阈值滤掉，或校验失败丢弃 |
| 力反馈 | ❌ 不支持 | ✅ 可读位置 / 负载 / 电压 / 温度 / 电流 |

所以第二代的核心决策不是「换个牌子的舵机」，而是**换一类控制方式**：
让角度不再以模拟量的形式走在线上。噪声顶多让某一帧报文作废，**不可能被误解成指令**。

> 这笔账值得算清楚：一代最后在信号线两端加电容电阻（100Ω 串阻 + 对地 4.7nF），
> 成功率也就 70–85%，而且是在**信号完整性层面打消耗战**。
> 换架构前期成本高（要重做协议、重做机构件），但一次性把这类问题从根上删掉了。

# 二、这一代做了什么

```
┌──────────────────────────────────────────────────┐
│  应用层   Vue 3 控制台  │  Python 手势控制          │
└───────────────────┬──────────────────────────────┘
                    │ HTTP
┌───────────────────▼──────────────────────────────┐
│  云服务层  Node.js + Express + WebSocket 中转       │
│           MySQL 持久化  │  OpenAPI 接口文档          │
└───────────────────┬──────────────────────────────┘
                    │ WebSocket 长连接（设备主动连出）
┌───────────────────▼──────────────────────────────┐
│  嵌入式层  ESP32-S3  自实现的 STS/SCS 协议栈        │
└───────────────────┬──────────────────────────────┘
                    │ TTL 半双工串口 · 1Mbps
┌───────────────────▼──────────────────────────────┐
│  硬件层    微雪总线舵机转接板(H2) │ STS3215 × 6     │
│            3S 锂电 12.6V 直通 │ 3D 打印件（SO-ARM101）│
└──────────────────────────────────────────────────┘
```

**硬件换了**：模拟舵机（MG996R × 5）→ 总线舵机（STS3215 × 6），
结构件跟着换成 SO-ARM101 的打印件。舵机 ID 出厂全是 1，必须逐个改成 1~6，否则总线冲突。

**协议自己实现**：没有用现成库，直接按 STS/SCS 协议写报文
（`sendPacket` / `writeWord` / `syncWritePosition`）。
多轴同步用 **SYNC_WRITE** 一条指令广播，不需要像一代那样在主循环里逐度插补——
**选对架构之后代码反而更简单**。

**顺带拿到的能力**：回读舵机的只读寄存器区（位置/负载/电压/温度/电流），
于是有了力反馈仪表盘、碰撞感知（负载突变）、过温与低压保护。

**软件栈也换了**：JSON 文件 → MySQL；原生 JS → Vue 3 + Vite；
新增 OpenAPI 文档、设备鉴权、登录鉴权与限流。

# 三、上机过程记录 ★

这一节是全文最有价值的部分。**下面每一个坑都是真卡住过的**，
而且共同点是：**现象都在骗你**——报错指向的地方，往往不是出问题的地方。

## 坑 1：总线自检全是 ✗，6 个舵机一个都读不到

**现象**：开机横幅打印 `总线自检: 1✗ 2✗ 3✗ 4✗ 5✗ 6✗ (0/6)`，死一样的安静。

**排查**：当时怀疑过舵机 ID 冲突、波特率不对、协议写错。
写了一个**极性扫描固件**（`hardware/polarity-scan/`），在不拔线的情况下
把 TX/RX 两种极性的四种组合都试一遍，自发自收——**一个字节都收不到**。

**根因**：ESP32-S3 开发板上**印着 `TX` / `RX` 的那两个脚是 GPIO43/44（UART0 的调试口）**，
不是固件里写的 GPIO16/17。线接在丝印那两个脚上，固件却在 16/17 上收发，
等于两根线接在了完全无关的引脚上。

**修法**：接到 H2 的三根线改用 GPIO16/17。

```
ESP32 GPIO16 (TX) ──→ H2 的 TX      ← 直连，不交叉
ESP32 GPIO17 (RX) ──→ H2 的 RX
ESP32 GND         ──→ H2 的 GND
```

> **直连不交叉**这件事也反直觉：板子上印的 TX/RX 是**从主控视角**标的
> （"你的 TX 接这儿"），所以对主控来说是 TX→TX。

**教训**：**别从协议层查起。** 一上来去翻 STS 协议手册、查校验和怎么算，
是在最不可能出错的地方花时间——而这个坑连一个字节都没上过线。
**「完全静默」这个症状本身就指向物理层**：协议错了通常会有乱码回包，而不是什么都没有。

## 坑 2：引脚改对了，还是读不到——回包开头被顶坏

**现象**：仍然 0/6，但这次**偶尔能收到东西**，而且字节是乱的：

```
FE FE 00 FE | FF FF 01 02 00 FC
```

前 4 个字节是垃圾，从第 5 个字节起才是正常的报文头 `FF FF`。

**根因**：这是**半双工**总线——一根线上既要发又要收，发完必须把线让出来。
原来的代码是这么"让"的：

```cpp
pinMode(SERVO_TX, INPUT);      // ← 这行不够
```

实测**摘不掉 UART**：ESP32 的 GPIO 矩阵会把引脚一直钉在 TX 输出上，
只改方向寄存器没用。于是自己刚发出去的尾巴还留在线上，
和舵机的回包叠在一起，把开头 4 个字节顶坏了。

**修法**：必须先把引脚从 UART 的输出矩阵上摘下来，收完再挂回去：

```cpp
// 发包后：真正释放总线
esp_rom_gpio_connect_out_signal(SERVO_TX, SIG_GPIO_OUT_IDX, false, false);
pinMode(SERVO_TX, INPUT);

// 收完包：挂回 UART
pinMode(SERVO_TX, OUTPUT);
uart_set_pin(UART_NUM_1, SERVO_TX, SERVO_RX, -1, -1);
```

**教训**：**「改方向」不等于「交出控制权」。** 外设（UART）一旦接管了引脚，
只在 GPIO 层面动手是摘不掉的。看到"回包开头固定几个字节是垃圾"这种症状，
就该想到**总线上有第二个人在说话**——而那个人是自己。

## 坑 3：好不容易读到了，网页发指令舵机却一动不动

**现象**：总线自检正常，遥测数字在跳，但**网页上拖滑块舵机毫无反应**，
而且舵机**松松的**，用手能掰动。

这个现象极其像"网页控制坏了"——很容易一头扎进 WebSocket 和前端代码。

**排查**：串口发一个 `S` 命令查状态，一秒确诊：

```
扭矩: 关   低压锁存: 是（会松力）
```

**根因**：低压保护**正确地工作着**。台面调试用的是 **C001（7.4V 级舵机）经 UBEC 供 5.1V**，
而固件里的低压阈值是按 **12.6V 的 3S 锂电**设的（`VOLT_WARN = 10.5V`）。
于是在固件看来"电池快没电了"，连续约 10 轮遥测后锁存 → `setTorque(false)` → 舵机松力。

而命令路径里**没有任何地方会重新 `setTorque(true)`**——一旦锁存就一直是松力状态。

**修法**：台面临时把 `VOLT_WARN` 降到 45（4.5V）。
并且让 `S` 命令在检测到 `VOLT_WARN < 100` 时**自己多打两行警告**：

```
⚠️  台面模式: VOLT_WARN=45（即 4.5V），低压保护已降低。
    接 12.6V 3S 锂电之前必须改回 105！
```

这样"忘记改回去"这件事就**不依赖人的记性**了——排查状态时看到这行，就知道当前是台面值。

**教训**：**保护逻辑正确工作，也会伪装成"功能坏了"。**
"舵机松 + 遥测正常 + 网页指令无反应"这个组合，指向的是**扭矩状态**，
不是通信链路。以后见到类似症状，先查"设备是不是自己主动停下了"。

## 坑 4：识别出来的手势，网页滑块不动

**现象**：手势识别正常（画面有骨架、日志有触发记录），**力反馈仪表盘在跳**，
但**滑块纹丝不动**。

**根因**：不是链路问题——是**滑块的语义**。翻前端代码：

- 力反馈仪表盘 ← `/api/telemetry`（机械臂的**实际**状态）
- 滑块 ← 本地 `angles`，**只有用户自己拖才会变**

滑块代表的是「**你想要的角度**」，不是「机械臂现在在哪」。
手势客户端改了机械臂的真实位置，仪表盘跟着跳，但滑块当然不动。

设计上说得通，但**演示时这就是坏的**——手势驱动机械臂，最该动的滑块反而不动。

**修法**：加了遥测同步（`syncFromTelemetry`），并留了一个**1.5 秒豁免期**：
刚下发过指令的关节不覆盖，否则遥测报的还是舵机没转完的旧位置，
会把用户正拖着的滑块**从手指底下拽回去**。

> 细节：同步用的是遥测里的 `deg`，不是 `pos`。
> `pos` 是舵机的**原始寄存器值**（0–4095），直接塞进 0–180 的滑块会得到一个莫名其妙的角度。

## 坑 5：手势命令根本没发出去——登录少发了一个字段

**现象**：骨架有、日志有、手势也触发了，机械臂不动。而日志里明明写着：

```
⚠️  登录失败：密码错误
```

**根因**：客户端登录时**只发了 password**，没发 username。
而服务端是 `accounts.login(username, password)`——拿 `undefined` 去查必然"查无此人"，
一律返回 401。**而 401 的文案是「用户名或密码错误」**——
报的是密码错，真正缺的字段完全看不出来。

**两个放大器让这个 bug 特别难查**：

1. **失败是静默的**。动作函数的返回值没人检查，登录失败只在启动时打一行字，
   之后照常运行——画面照样有骨架、照样报手势。**静默失败比崩溃难查得多。**
2. **日志是空的**。Python 的 stdout 在输出重定向到文件时是**块缓冲**（攒够 8KB 才落盘），
   「登录失败」那行一直卡在缓冲区里，进退两难：看日志什么都没有，
   程序却在正常运行。

**顺带一个副作用**：每次启动都白送 **5 次失败登录**，
正好撞上登录接口的防爆破限流（同 IP 连错 5 次封 15 分钟），
**把网页登录一起封掉了**——症状是"我明明密码是对的，怎么说我尝试过于频繁"。

**修法**：
- 登录带上 `username`（`--username` / `ARM_USERNAME`）
- 发送失败**必须可见**：打印 + 画面上红字提示
- stdout 改**行缓冲**
- 429（被限流）单独报，不和"密码错"混为一谈

**教训**：**错误信息会把人带偏。** 「用户名或密码错误」这句话让排查方向
从一开始就锁死在"密码对不对"上，而问题在两米之外。
**报错文案值得当代码一样认真写。**

## 坑 6：叠加层的中文全是问号

**现象**：预览窗口上本该写着「模式: 指令」的地方，显示的是 `??????: ???`。

**根因**：OpenCV 自带的 Hershey 字体**只有 ASCII**，
`cv2.putText` 画中文会退化成问号——而且是**每个 UTF-8 字节一个**问号
（一个汉字 3 个字节 → 3 个 `?`）。

**这个坑的恶劣之处**：程序本身**完全正常**，识别、触发、发送全对，
只是"字没画出来"。而界面上一个能读的字都没有，
人很容易判断成"识别没出来"，然后去查 MediaPipe。

**修法**：中文改走 PIL + 系统中文字体（苹方）渲染成小图块，
再按 alpha 贴回画面，并按「文字 + 字号 + 颜色」缓存——这几行字每帧都长一样，
没必要每帧重排。

顺手把模式做成了**顶部整条横幅**（绿 = 指令模式，蓝 = 跟随模式），
窗口标题栏也跟着变。

## 坑 7：文档在说一代的硬件，而且型号会让人买错东西

**现象**：核对文档时发现，`技术文档.md` 里**整节整节描述着一代的硬件**——
架构图还写着 `PCA9685 驱动板 │ 舵机 × 5`，数据流第 ⑦ 步是「写入 PCA9685」，
第三节整节在讲模拟舵机的脉宽原理；README 的硬件清单里也还挂着 PCA9685。

**根因**：**代码和硬件一直在往前跑，文档停在 09-18 那个版本。**
改硬件时改了固件、改了接线、改了口诀，但"顺手更新文档"这件事没有一次是被单独安排的，
于是文档慢慢变成了一份**描述着已经不存在的系统**的说明书。

**比"过时"更糟的一处**：硬件清单里舵机型号写的是 **7.4V、1/345 减速比**——
这是 **C001（Leader 臂用）**的参数。而 Follower 臂必须用 **C047（4–14V）**。
**照这份清单下单，买回来的 6 个舵机接上 12.6V 会直接烧掉。**

> 这说明文档漂移不只是"不好看"：**错误的技术参数是会花钱的。**

**修法**：把 `技术文档.md`、`README.md`、`arm-bus-servo/README.md`、
`arm-cloud-bus/README.md`、`server/README.md`、`server/swagger.js`
里描述一代硬件的段落全部按实物改写；
一代的内容不删，**明确标注为历史**并链接到 `robot-arm 1/`。

**顺带发现的第二类错误**：`arm-cloud-bus/README.md` 的接线图把 TX/RX 写反了
（写成 GPIO17 发、GPIO16 收），和固件里的 `SERVO_TX 16 / SERVO_RX 17` 正好颠倒——
**照它接线，总线一个字节都收不到**。同一份文档还留着"回读需要加 1kΩ 上拉"的旧结论，
而那个问题早就用软件解决了（见坑 2）。

**教训**：**改硬件时，文档要和固件一起改，当成同一件事。**
判断该不该改的标准很简单：**这句话现在还是真的吗？**
如果描述的是"以前那套"，就把它标成历史，而不是留在原地假装是现状。

## 坑 8：六颗舵机出厂全是 ID 1，全接上总线就互相打架

**现象**：整条菊花链接好之后，PING 的回包时好时坏，而且大多是乱码：

```
#1: 00 00
#3: FF 40 20 FC
#4: 00 00 F8
#5: FF FF 01 02 00 FC   ← 偶尔一条完整
```

**排查**：单独只接一颗舵机，**10/10 全部干净**；六颗全接上就变成 3/10。
把每颗**单独**接到转接板上逐颗改 ID（1~6），问题消失。

**根因**：出厂 ID 全是 1。六颗同时收到 PING、同时应答，
半双工总线上几个回包的波形直接叠在一起——不是"某个字节错了"，
是**两条包在物理层撞车**。所以校验和当然对不上。

**教训**：**「时好时坏」比「完全不通」更值得怀疑撞号。**
完全静默是物理层问题，随机乱码往往是多个设备同时在说话。
判断方法很简单：**只留一颗，看回包是否 10/10 干净**。

## 坑 9：舵盘是在任意角度装上去的，上电"回中"等于让关节甩半圈

**现象**：ID 改完、总线 6/6 全通，但按原固件上电，六个关节会分别要转：

| 关节 | 当前 raw | 固件要去 raw 1024 | 要转 |
|---|---|---|---|
| 肩部 | 2818 | 1024 | **−158°** |
| 腕旋转 | 3779 | 1024 | **−242°** |
| 夹爪 | 3619 | 1024 | **−228°** |

这种幅度会直接顶死在机械限位上。

**根因**：官方装配流程要求**先把舵机转到中位（raw 2048）再装舵盘**。
这台机器是在舵机任意角度下装好的，所以"90° 对应 raw 1024"这个假设
对每一颗都不成立，而且每颗偏得还不一样。

**修法（不拆机）**：用舵机自己的 **OFS 位置偏移寄存器（0x1F，EEPROM）**
把每颗的编码器零点挪开，让各自的机械行程居中到 raw 2048 两侧；
固件再改成**逐关节映射** `[RAW_MIN, RAW_MAX]`。

```python
# 读回来的语义（实测）：读数 = 编码器值 − OFS
# 写 OFS = 85 → 100（+15），位置读数立刻 −15
# OFS 在 EEPROM，需要先解锁（寄存器 55 写 0），写完再上锁
```

> **别急着拆舵盘。** 改 OFS 是标准校准手段，一次性、可回滚，
> 比把六个舵盘重新装一遍省事得多。

## 坑 10：舵机的目标位置是单向单调的，**不会走近路**

**现象**：底座在 raw 111，命令它去 raw 4090。按最短路径应该是 −10°，
实际它朝**正方向**走了 128°，撞在机械限位上停住。

```
111 → 207 → 686 → 1518 → 1572（不动了）
```

**根因**：STS3215 的目标位置是**线性单调**的解释，不是按 0–4095 取模走近路。
所以**一旦目标跨过 0/4095 边界，它不会绕回来，而是朝反方向转一大圈**。

**这直接决定了坑 9 的做法**：不能"读出来多少就按多少存，跨边界靠取模补"，
必须**先把行程用 OFS 挪进 0–4095 内部**，让任何目标都不可能跨边界。

**教训**：**别凭常识假设外设的行为。** "绝对编码器当然走最短路径"听起来天经地义，
实测就是错的。拿一个**不会撞到东西的关节**（底座水平转盘）做一次低速实验，
两分钟就能证伪，比在真臂上赌一次便宜太多。

## 坑 11：自检里永远只有第一个舵机 ✗，换回 USB 模式又全好

**现象**：

```
总线自检: 1✗ 2✓ 3✓ 4✓ 5✓ 6✓  (5/6)
```

稳定复现，每次都是 ID 1。可它明明刚在微雪板 USB 模式下 10/10 正常。

**根因**：**上电后第一个被访问的舵机，第一帧会被吃掉**。
循环从 0 开始，ID 1 永远排第一，所以永远中招；2~6 因为总线已经"热"了都正常。

**修法**：`servoBus.begin()` 之后 `delay(300)` + 清空缓冲；`pingServo` 内部重试 3 次。

**教训**：**"某个固定位置永远失败"通常不是那个位置坏了，而是它是第一个。**
和坑 1 正好相反：坑 1 是接线错在第一个，这个是时序错在第一个。
两者现象都长得像"底座舵机坏了"。

## 坑 12：一连 WiFi 就 `Brownout detector was triggered`，无限重启

**现象**：日志里 `连接 WiFi: xxx E BOD: Brownout detector was triggered`，
然后复位、重新开始，循环。

**根因**：ESP32 由**电脑 USB 供电**，WiFi 发射瞬间的电流尖峰把 3.3V 拉塌。
供电能力是这类"连网就重启"的常见根源，换固件没用。

**修法**：`WiFi.setTxPower(WIFI_POWER_8_5dBm)`——用一点信号余量换供电稳定。
换根好线 / 换个直连的口也有效；还不行就降到 `WIFI_POWER_5dBm`。

**教训**：**Brownout 是电源问题，不是软件问题。** 但软件确实能缓解，
先把发射功率降下来，比换板子快。

# 五、这套排查方法，沉淀下来

这一代踩的坑，回头看**有一半是可以避免的**——如果把下面几条当纪律：

1. **症状「完全静默」→ 先查物理层。** 一个字节都收不到，不可能是协议里的校验和写错了。
2. **别从里往外查，从外往里查。** 线、电、地、方向——这些确认完再翻协议手册。
3. **「改方向」不等于「交出控制权」。** 外设接管了引脚，只在 GPIO 层动手摘不掉。
4. **保护逻辑会伪装成故障。** 设备主动停下来的时候，看起来和"坏了"一模一样。
5. **静默失败比崩溃难查。** 该吵的地方就要吵——返回值要检查，错误要打出来、画出来。
6. **报错文案是代码的一部分。** 一句指向错误的报错，能让人在两米外的地方找一整天。
7. **用最小固件复现。** 极性扫描、回环测试、关 WiFi 锁死——这些"没用"的小固件
   往往比主程序更快给出答案。
8. **把「为什么」写进 commit 和文档。** 半年后你还认得出自己当时在想什么。
9. **改硬件时，文档和固件一起改。** 文档漂移不只是"不好看"——
   一份写着 7.4V 型号的硬件清单，是会让人买错、烧掉东西的。
   定期问一句：**这句话现在还是真的吗？**

> 面试里比"我会用什么框架"更有说服力的，是**"我为什么从 A 换到 B"**，
> 以及**遇到全无线索的问题时，我是怎么一步步缩小范围的**。
